# MPVFlow: on-device motion-interpolation experiment

## Goal

MPVFlow is the app's local motion-estimation/motion-compensation (MEMC) frame-interpolation path. It runs on-device, uses the selected compute backend, and does not depend on an off-device service.

This is an independently written prototype informed by public descriptions of frame-rate conversion. It is not SVPFlow source code, does not reproduce proprietary defaults, and is not claimed to be pixel-identical to SVPlayer.

## Active GPU implementation

### MPV `gpu-next` route

When MPVFlow is eligible on the MPV engine, the app selects the `gpu-next` renderer with Vulkan. The patched MPV video output supplies source-frame textures and display-timed output ticks to the shared Flow implementation. The renderer API and interpolation compute API are separate choices: Vulkan remains the MPV renderer even when Flow's motion and synthesis kernels use OpenCL. In the Flow path, the timestamped source mix, pair analysis and offscreen synthesis are prepared and flushed before `pl_swapchain_start_frame`; this allows submitted GPU work to overlap a blocking acquire call, but does not make WSI acquisition nonblocking or prove the frame was scanned out.

### OpenCL compute backend

The app now has a real OpenCL path, not a settings-only toggle. It dynamically loads the optional Android `libOpenCL.so`, compiles the Flow kernels at runtime, and imports shared Android `HardwareBuffer` BLOB allocations through Qualcomm's `cl_qcom_android_ahardwarebuffer_host_ptr` extension. Vulkan copies RGBA8 images to/from those shared buffers; OpenCL performs multi-scale luma/motion analysis, scene-cut detection, confidence/consistency checks, and full-resolution synthesis. The generated image returns to the Vulkan renderer. Pixel data is not copied through the CPU and there is no CPU pixel readback path.

The current OpenCL interop implementation is **Qualcomm/Adreno-specific**. OpenCL enumeration alone is not enough: the runtime extension, Vulkan external-memory/foreign-queue support, compatible RGBA8 transfer usage, buffer import probe, and kernel build must all succeed. `Auto` uses Vulkan/SPIR-V on the renderer's native queue to avoid cross-API ownership transfers and per-frame queue finishes. OpenCL remains an explicit experimental choice and does not silently switch to Vulkan: initialization or runtime failures are diagnosed and affected frames pass through. Other vendors' OpenCL import extensions are not implemented yet.

For conservative cross-API correctness, this first bridge serializes Vulkan buffer copies and OpenCL work with Vulkan fences and `clFinish`. This avoids CPU pixel copies but can add substantial blocking overhead. It is an initial functional backend, not evidence that it improves cadence on every device; it needs measurement on the target phone before being recommended as faster.

### Vulkan compute backend

The Vulkan/SPIR-V backend remains available explicitly and as `Auto` fallback. It uses libplacebo passes on the renderer's Vulkan device. Motion analysis is bounded to a reduced working size; source copies and synthesized processing images are bounded by the configured synthesis maximum dimension (1920 px by default), then rendered into the active swapchain target. That target can differ from both source and synthesis dimensions. MPV's `vo->params` describes configured video parameters, not the swapchain raster; diagnostics therefore report presentation-target texture size separately. Unsupported input or a deadline miss uses original source frames rather than stalling playback.

Both Vulkan and OpenCL finer pyramid levels now retain the parent block's normalized SAD and best-versus-runner-up uniqueness. If the parent has high residual (`>0.12`) but is not an exact tie (`uniqueness >0.0005`), that level doubles its local search radius up to 16; reliable or fully tied parents keep the original radius. A deterministic synthetic translated-texture test recovers 9–12-pixel misses beyond the base radius, at the cost of extra SAD comparisons. Motion-grid allocation now avoids duplicate terminal blocks, and interpolation maps the final partial interval to the actual clamped block origin for Vulkan and OpenCL, including coarse-to-fine search prediction. The exact Vulkan shader pixel oracle includes a small irregular-grid case that rejects the former uniform-coordinate result; this is a deterministic CI regression, not device quality evidence. These are bounded source-level improvements, not a Neural ODE/SciFlow implementation or evidence of on-device speed/quality gains. Forward–backward cycle consistency and source-frame fallback remain the separate inference-time safeguards for poor matches and occlusions.

An earlier Vulkan synthesis change converted fine-block center positions to block-origin coordinates using the then-existing `origin + 2` edge-guide convention; the pixel-index centroid correction below supersedes that half-pixel assumption. This corrects a two-analysis-pixel alignment mismatch for spatially varying motion, including zooms, without changing the matcher, grid density, search radius, output size, or smooth source-crossfade fallback. Soft Blend and Visibility Resolver policies remain unchanged. Exact pixel and mutation fixtures guard the coordinate correction; device testing is still required to establish whether the reported pixelated patches are eliminated or FPS changes.

The default Vulkan synthesis policy now fades between source-space crossfade and motion-warped output instead of switching at the former 0.28 confidence contour. Inverse-warp reliability fades from 0.25 to the existing 0.75 output-pixel rejection ceiling; luma, chroma and neighborhood conflict trust fades before the existing hard rejection boundaries. This targets block-shaped patches where neighboring pixels selected different coordinate spaces, not smooth whole-frame ghosting. Fully trusted motion retains its warp-only fast path, and static pixels, scene cuts and non-finite rejection remain guarded. No motion-search, grid-density, frame-rate target, output-resolution or extra-pass change is involved; transition pixels do need source samples, so phone performance still requires measurement. The actual Vulkan pixel oracle reproduces the old confidence seam (50 to 40 from adjacent half-float confidence values) and boundary seam (50 to 61 from a one-level source change); the continuous policy bounds both changes to one level in those fixtures. Mutation checks restore each hard contour and must fail. These fixtures demonstrate the mechanism, not proof that all supplied anime artifacts or Media3 pacing fluctuations are eliminated. The explicit OpenCL backend is unchanged.

### Hierarchical predictor registration

Both Vulkan and OpenCL formerly looked up the parent motion field at `child_origin / 2`. A parent vector represents the center of an 8x8 parent block, not its origin. With 2x box downsampling, center-to-center registration followed by conversion back to a parent-block origin gives `child_origin / 2 + child_block_size / 4 - 4`. Thus the 8x8 middle search needs an offset of -2 parent pixels and the final 4x4 search needs -3, in both axes. The old lookup spatially leads the intended predictor by half to three-quarters of a parent grid step. Near independently moving objects that can change the seed, its residual/uniqueness, and the limited search neighborhood, regardless of Soft Blend or player engine. Hardware-indexed seeds are unchanged.

The production matchers now use this block-size-aware registration without altering grid density, search radius, pass count, resolution, or output cadence. The Vulkan oracle retains its original outlined-pan test and adds explicitly separate adversarial parent-field sentinels for both child sizes, with the actual 8x8 parent grid and radius-4/radius-8 searches. Corrected probes retain the known (3,0) translation; baseline `fa339c7b`, old origin-only sampling, fixed -2 at the fine level, and fixed -3 at the middle level each fail the corresponding targeted probe. These tests prove coordinate registration, not that all synthetic/adversarial parent vectors are good or that the phone recording's artifacts have been eliminated. The sentinel's aggregate motion-error counts are not a quality-improvement metric. OpenCL receives the same formula and structural coverage; no Android OpenCL-device execution is claimed.

The suggested [MVTools documentation](https://github.com/pinterf/mvtools/blob/mvtools-pfmod/Documentation/mvtools2.html) also explicitly warns that zero block overlap can cause blocking-like artifacts, while greater overlap increases block count and reduces processing speed. Our final 4x4/stride-4 estimation is non-overlapped; the 8x8/stride-4 parents overlap. This motivates a separate measured overlap/coverage/occlusion experiment, not an unmeasured density increase in this correctness patch. MVTools is an AviSynth plugin and its source headers specify GPLv2-or-later; no MVTools implementation was copied or linked. Its documented concepts are comparison material, not proof that our continuous inverse-warp synthesis is identical to block compensation.

### Soft Blend compositing continuity

Both engines pass the same shared Vulkan synthesis shader `soft_blend=true` and `preserve_motion_blend_on_conflict=true` when the debug Soft Blend setting is enabled. The default-only fixes do not automatically repair that opt-in path. At `fa339c7b`, the actual production shader changes a probe from 46 to 40 across adjacent half-float confidences around 0.28, and from 50 to 57 across a one-level source change at the luma-conflict boundary. The default policy already passes those same contour fixtures. The pixel harness now runs them for default, Soft Blend, and production preserve-motion Soft Blend, rather than skipping the opt-in cases.

Soft Blend now retains its existing bounded temporal conflict fallback, then continuously mixes toward its visibility-normalized endpoint warp using confidence and boundary trust. It no longer chooses the two composites with a binary confidence/conflict branch. Vanishing visibility weights fade to fallback without a denominator cutoff jump. The low-confidence shortcut is exact while both visibility weights are zero. The production Soft Blend probes now change 43 to 43 and 56 to 57 respectively. Independent mutation controls restore each discontinuity and must fail, and `--soft-blend-baseline-revision fa339c7b` demonstrates the before/after difference with the default path as a control.

This changes no target FPS, source/output resolution, motion-grid density, search radius, or pass count. Some formerly early-returning transition pixels now evaluate boundary trust, so device GPU cost still needs measurement. It is a verified compositing defect, not a claim that all moving-character/camera artifacts are resolved: the user also observes artifacts with Soft Blend disabled, and shared motion estimation remains a separate concern.

### Residual source overlays during changing motion

The inverse warp previously used two fixed-point updates, `a = p - t * F(a)`, before checking its final residual. A valid invertible spatially varying field need not converge under that update. For an affine field with derivative `D`, the iteration's error multiplier is `-t * D`; invertibility of `I + t * D` is not a convergence guarantee. Rejected or partially trusted pixels then mix the unaligned source frames back into the output. That preserves temporal fallback but also exposes previous/current silhouettes alongside a successfully warped intermediate silhouette. Spatially varying rejection across the reduced motion grid can produce block-shaped patches; it does not mean the full-resolution output image was downscaled to the analysis grid.

Synthesis now derives the bilinear field's Jacobian from the same four loaded motion texels and replaces the existing two updates with bounded Newton updates. It differentiates the actual shortened terminal interval and uses zero derivative in the clamped exterior. Nonfinite, small/nonpositive-determinant, or over-one-grid-cell-per-axis corrections retain the old fixed-point update. The final 0.25–0.75 **output-pixel** residual fade, bidirectional cycle, frame bounds, photometric checks, source fallback, and scene-cut handling are unchanged. Both MPV and native Media3 use this shared Vulkan shader. This does not change target FPS, resolution, analysis density, search radius, GPU pass count, or motion-texture read count; additional arithmetic still needs on-device timing. The separately selected experimental OpenCL synthesis is not changed or claimed to have this correction.

Soft Blend also excluded the existing stringent coherent-aperture recovery. A coherent outline with normalized SAD `0.0078125` and uniqueness `0.1875` retained an old-position ghost of 13/255 with the production preserve-motion policy, while default synthesis recovered the same outline. Both policies now qualify that support using the same unchanged residual, cycle, trajectory-coherence, interior-bound, and full-resolution RGB conditions. This is not a blanket increase in ambiguous-vector confidence.

The actual production-shader oracle adds analytically corresponding camera zoom/rotation ramps at quarter, half, and three-quarter timesteps, plus whole-outline old/new-position checks for tied and low-uniqueness coherent pans. All three synthesis policies are exercised. `--inverse-baseline-revision 273d3a4b` proves the camera-motion regression fails the last user-tested shader with Soft Blend both off and on. Independent mutations restore fixed-point-only inversion and the Soft Blend aperture exclusion; each must fail its targeted fixture. A deliberately nonconverged inverse still exercises the unchanged residual guard. These regressions demonstrate specific failure mechanisms, not a complete reconstruction of the supplied anime's source frames or proof that every device artifact is eliminated. The supplied output-only screenshots/recording and runtime logs cannot identify every rejected pixel without source-pair/motion/decision capture.

### Native Media3 route

The separate Native Media3 route uses a Vulkan renderer/context and the same Flow compute API preference. Its decoded surface is captured on GLES, with Vulkan handling Flow buffers and the final display handoff; interpolation itself uses either the selected supported OpenCL route or Vulkan/SPIR-V. Capture/production and presentation run on separate GL handlers/contexts, connected by a bounded three-slot queue and producer/consumer GPU fences. A slow `eglSwapBuffers` does not directly block the capture handler, but GPU saturation and replacement of already-synthesized queued frames can still waste work and raise latency. Although a device may expose a dedicated compute family, Media3 intentionally keeps `async_compute` and `async_transfer` disabled: its imported AHardwareBuffer images are created with exclusive sharing, while the current libplacebo wrapper contract requires multi-family images to be concurrently shared. Diagnostics report available dedicated-compute families without selecting one. Imported images and presenting slots must not be recycled before their completion fences. MPV's `gpu-next` setting does not select the Native Media3 route's renderer.

Both Vulkan contexts opportunistically request `VK_NV_optical_flow`, its feature bit and an optical-flow queue family where available. When the device also supports compatible image formats and timeline synchronization, the shared core creates two NV sessions (one for each direction), dispatches full-resolution `R8_UNORM` frame luma without CPU readback, and samples the device's S10.5 motion-vector maps as centers for the existing coarsest-level SAD search. The SAD match, ambiguity/confidence checks, forward/backward consistency, occlusion handling, and source-frame fallback remain authoritative; hardware vectors are never treated as verified final motion. Image/session/queue setup failure or a busy nonblocking command ring falls back to the ordinary bidirectional block matcher. The runtime logs distinguish capability, successful session setup, actual optical dispatch, and fallback. This optional path is an implementation change, not evidence that either engine sustains its requested frame rate or is artifact-free on a device.

The shared core also queries optional `VK_QCOM_image_processing` / `VK_QCOM_image_processing2` support, feature bits, block-match region/window limits, and exact image-format usage support. When both extensions/features and all required usages are enabled and supported, the optional adapter converts the already-downsampled luma frames into QCOM-compatible staging images, copies them into block-match images, and runs the QCOM2 window-SAD intrinsic to produce coarse vector candidates. It seeds the existing coarsest-level motion search only; every candidate is checked against the existing SAD objective, the full clipped center-out search remains in force, and forward/backward consistency, confidence checks, occlusion handling, and source-frame fallback remain authoritative. If setup, synchronization, a nonblocking command slot, or dispatch fails, the adapter falls back to the full baseline SAD search. Runtime logs distinguish capability, image setup, active dispatch, and fallback. The extra conversion/copy and device-specific intrinsic behavior have not yet been verified on the target phone, so this implementation is not evidence of a cadence or quality improvement. A device profile containing only legacy `VkFormatProperties` does not establish the newer QCOM `VkFormatFeatureFlags2` result; the runtime diagnostic and on-device validation are required.

The current support policy keeps HDR, Dolby Vision, DRM, rotated, and non-square-pixel content on Media3's standard renderer. Unsupported formats or tight deadlines fall back to source frames.

## Cadence and device constraints

The effective Flow target is capped to Android's reported display refresh; this cap is disclosed and is not presented as proof that a selected target was achieved. The app's performance/quality profile maps the longest-side motion-analysis budget monotonically across 480–640 pixels through 60 fps, 384–480 at 72–90, 320–432 at 96, 384–448 at 120, and 288–320 at 144. At 120 fps, the balanced profile is 416 pixels; the four-pixel vector spacing remains unchanged, giving a modestly denser analysis grid. The native renderer applies only the target-rate safety ceiling, so the quality profile is not expanded and clamped a second time. These are processing-size limits, not promises of encoded output resolution or sustained performance.

Media3 retains its additional 96-pixel analysis allowance, capped at 640, but now uses the same target/quality-dependent coarse search radius as MPV instead of always searching radius 8. At 120 fps and quality 60, the radius is 4 on both engines; the bidirectional pyramid, adaptive local search and synthesis safety checks remain unchanged. A failed Media3 producer submission no longer consumes its output tick, so a later callback can retry it.

The supplied Media3 log at `8484a876` recorded roughly 49 successful EGL swap returns per second, about 5.24 ms lifetime-average synthesis time, and 1,919 coalesced presentation frames alongside 6,408 synthesized successful outputs. Swap waits reached tens of milliseconds with no output-submission failures. Coalescing happens after synthesis, so some expensive GPU work never reaches presentation. Media3 now checks non-mutating queue admission before source staging or synthesis: an already-complete READY frame is retained, and a new output is deferred until no READY frame remains and a FREE slot exists. Consumer acquisition and fence completion wake the coalesced producer task so admission does not impose a fixed 60-fps limit or depend only on the next display callback. Deferred work does not consume an output tick or count as a failed GPU submission; resumed tick gaps and `backpressureDeferredOutputs` are reported separately. No presenting buffer is reclaimed early and synchronization remains unchanged. This removes a demonstrable source of wasted work, not proof that the phone now sustains 120 fps. These metrics measure submission/swap-return cadence, not physical display scanout.

MPV synthesis admission uses fixed monotonic target-rate buckets rather than delaying a full interval after every late callback. This prevents callback frequency and integer rounding from systematically lowering the admitted rate. Redundant callbacks may hold the last synthesized image for less than one target interval only while its source pair, forward-moving PTS, color, pixel aspect and synthesis policy remain compatible. The cache is invalidated with its owning pair; original-frame fallback remains available when those checks fail. These changes address generation continuity, not proof of displayed 120 fps or artifact-free motion.

For the MPV Vulkan renderer, Flow requests Vulkan `mailbox` presentation before creating `gpu-next`, so stale queued images can be replaced without lowering the selected target rate. An explicit `vulkan-swap-mode` in `mpv.conf` remains authoritative. libplacebo falls back to FIFO when the Android surface does not support mailbox mode; the request is not a guarantee of achieved cadence, and the current device logs do not identify the selected mode. Runtime diagnostics separate image-acquisition and blocking `swap_buffers` waits from nonblocking submit duration. These CPU timings do not measure SurfaceFlinger scanout or prove every generated frame was displayed.

Interpolation is intended for compatible SDR progressive video. The active Android path can use MediaCodec direct mode or `mediacodec-copy` for decoder input, depending on APK capabilities; decoder-input copying is distinct from GPU-side synthesis and does not imply CPU readback of generated frames. Actual smoothness, artifacts, displayed cadence, A/V sync, detail, power, and thermal behavior must be measured on target phones. No claim of sustained 144 fps or SVPlayer parity is made before device testing.

### Fine-flow pixel-centroid registration

The `163e6ef6` phone logs still show 120-fps Flow with Soft Blend and the optional visibility resolver disabled. Both engines use shared Vulkan synthesis. Disabling Soft Blend does not disable ordinary confidence/conflict fallback: the default shader still crossfades unwarped endpoints when support is rejected, and partially reintroduces them when warp trust is below one. Executing the production shader with exact translation but rejected reverse support reproduces endpoint outlines instead of the intermediate outline. This establishes a possible artifact mechanism, not pixel-level attribution of the supplied screenshots: their logs have no per-pixel confidence or decision capture.

An independently reproducible coordinate error exists in the active shared shader. Fine SAD blocks sample pixel indices `p + {0,1,2,3}`, so their centroid in the texel-index coordinates used by `flowP` and `colorAt` is `p + 1.5`, not `p + 2`. Both bilinear lookup and its analytic Jacobian now subtract 1.5 before mapping to block origins. The former offset spatially displaced varying vector/quality fields by half an analysis pixel; this does not imply a fixed half-pixel displacement of the final image. Constant translation fields are unaffected, so this correction alone cannot establish elimination of all pan/occlusion ghosting.

Earlier affine fixtures injected vectors at `origin + 2`, repeating the implementation's coordinate assumption. They now independently derive the location from the mean of the actual SAD sample indices. Exact ramp/affine checks retain their one-level tolerance. Restoring the old 2.0 offset in both lookup and Jacobian must fail the rotation oracle in default and both Soft Blend policies. The parent-pyramid offset is unchanged: the 2x2 downsample's half-pixel center cancels the pixel-index centroid adjustment. No target cadence, output resolution, format, temporal alpha, confidence threshold, GPU pass or fetch count changes.

The optional visibility resolver and legacy OpenCL synthesis have separate coordinate conventions and are not changed by this focused active-Vulkan correction; neither was active in these runs. End-to-end estimated-flow replay and a paired real-scene capture remain necessary before declaring the reported character/pan ghosting solved. Cadence pressure is a separate measured issue, not proof of the screenshot's per-pixel cause.

# RIFE and mobile motion-interpolation notes

The requested implementation targets the existing `experimental-features` MPV filter path. RIFE-ncnn-vulkan is a frame-synthesis model: its `RIFE::process` API takes two RGB frames plus a timestep and returns a synthesized RGB frame. It does **not** expose a low-resolution optical-flow field for a separate MPV warp shader. Upstream's supported `uhd_mode` does, however, estimate motion from half-resolution inputs, rescale that flow internally, and synthesize a full-frame output; the prototype enables this mode. It does not produce a reusable 256×256/512×256 flow-map API. See the [RIFE-ncnn-vulkan source](https://github.com/nihui/rife-ncnn-vulkan) and its [RIFE implementation](https://github.com/nihui/rife-ncnn-vulkan/blob/master/src/rife.cpp).

The [Smoovie engineering article](https://grapheme.com.au/blog/how-smoovie-makes-24fps-look-like-60-inside-our-motion-interpolation-engine) describes a separate, non-neural MEMC design: CPU block-motion estimation and field cleanup are overlapped with GPU warping and paced presentation. It reports about 5.3 ms for CPU motion estimation and 11.1 ms for GPU synthesis at 1080p on a Snapdragon 865, and notes that GPU-only motion estimation starved the display path in its earlier tests. This supports measuring end-to-end presentation and dropped frames, not treating inference throughput as playback throughput.

The current RIFE filter is opt-in, defaults to 60 output fps, and offers selectable 30/48/60 fps targets. Its automatic processing cap is 480p for 60 fps, 720p for 48 fps, and up to 1080p for 30 fps; users can select another cap or source resolution. Only synthesized frames are processed at the selected cap and then upscaled to the source dimensions. SDR 10/12/16-bit input is converted through mpv's swscale path to the model's RGB24 input; HDR PQ/HLG, interlaced, and hardware-only frames remain pass-through. These caps improve the chance of fitting the frame budget but cannot guarantee it; per-stage timings and presentation rate still need device measurement.

SVPlayer's own [Google Play listing](https://play.google.com/store/apps/details?id=com.svpteam.svp&hl=en_US) and [Android FAQ](https://www.svp-team.com/wiki/FAQ_(Android)) describe the SVP motion-estimation/motion-compensation engine and recommend a strong CPU, reduced processing size, and Snapdragon 865-class performance for 1080p. The SilkPlay listing describes its “Smooth” feature as motion compensation without AI model downloads ([product listing](https://apkpure.com/silkplay-smooth-60fps-video/com.silkplay.player)). These are different algorithmic paths from RIFE-v4.6 neural synthesis; their advertised 60 fps demonstrates that on-device interpolation is possible, not that this RIFE Vulkan path will meet the same frame budget on every device.

## Verified bridge optimization

The pinned upstream RIFE CLI wraps decoded RGB24 storage directly as an external `ncnn::Mat` (`src/main.cpp` at commit `a7532fc3f9f8f008cd6eecd6f2ffe2a9698e0cf7`). Its Vulkan `RIFE::process_v4` then reads the Mat data as packed bytes, uploads it, and downloads RGB24 output into the supplied output Mat. The Android bridge had instead called `Mat::from_pixels`, which creates float-planar storage before `process_v4` interprets the pointer as packed bytes. The bridge now uses the upstream packed-byte view for both inputs and supplies the caller's output buffer directly, avoiding the redundant float conversion, temporary NCNN Mats, and output memcpy.

The pinned upstream RIFE explicitly disables FP16 arithmetic while enabling FP16 packed/storage. The Android build now enables the arithmetic path only when the selected Vulkan device reports native FP16 arithmetic support and ncnn does not flag its known implicit-FP16 driver bug; otherwise it keeps the upstream FP32 arithmetic default. Startup diagnostics report `fp16_arithmetic=0/1`. This is a conservative throughput experiment, not a measured speedup or visual-quality guarantee; the model's image quality and sustained cadence still need device testing. The Android bridge passes `uhd_mode=true`; upstream's UHD path halves the images for flow estimation, doubles the resized flow, and still synthesizes an output at the supplied processing dimensions. Since the Android filter also caps 60-fps processing at 480 pixels on the longest side, the flow-estimation input can be around 240 pixels before the flow is enlarged back to the 480-pixel synthesis size. Turning UHD mode off may retain finer motion detail but can increase Vulkan work substantially, so it should be benchmarked on-device rather than toggled speculatively. True AHardwareBuffer-to-Vulkan zero-copy still requires replacing mpv's software-readable RGB24 frame contract and correctly managing decoder-buffer lifetime and external-memory synchronization; it is a separate redesign, not a safe toggle.

## Implemented cadence and decoder hardening

The RIFE mpv filter now budgets total conversion, inference, and output work against 85% of the actual adjacent-source PTS interval, rather than comparing every inference to one target-frame interval. It estimates remaining work from recent measurements, fails open before continuing a predicted over-budget gap, and preserves the existing audio-master clock and ordered source PTS on fallback. RGB24 input conversion and packing are cached for all synthesized outputs between the same two source frames. A new stride-checked fast path lets the Vulkan inference write directly into mpv's synthesized RGB24 image when its rows are tightly packed; padded-stride images retain the existing scratch-buffer-and-copy fallback, so frame layout and output pixels remain correct.

The supplied 1080p SDR log showed inference at 480×270 taking about 39–77 ms, versus a measured source-pair budget of about 28–36 ms; the filter therefore correctly falls back instead of claiming 60-fps synthesis. The 3840×2160 PQ clip is separately and explicitly passed through as unsupported HDR. This change does not relax either boundary: late results are still rejected, and HDR PQ/HLG remain pass-through.

When RIFE is active and the app hardware-decoding preference is enabled, MPVView requests `mediacodec-copy,no` and sets `hwdec-codecs=all` unless `mpv.conf` owns that codec option. This retains MediaCodec decoding while exposing CPU-readable frames; it is not a zero-copy GPU path. The separate native cadence tests cover 30→60 and 24→60 scheduling, source-pair budget boundaries, and predictive fallback. Actual smoothness, thermal stability, A/V sync, codec coverage, and visual quality still require playback on representative Android devices; CI can verify compilation and unit logic, not certify those runtime properties.

## Next architecture-level improvements

For SVPlayer-class efficiency, keep MediaCodec surfaces resident and import supported `AHardwareBuffer` images into Vulkan, or use a decoder-native motion-vector/optical-flow path so full RGB24 upload/readback is avoided. Android's [AHardwareBuffer NDK API](https://developer.android.com/ndk/reference/group/a-hardware-buffer) and Vulkan's [Android external-memory extension](https://docs.vulkan.org/refpages/latest/refpages/source/VK_ANDROID_external_memory_android_hardware_buffer.html) provide the relevant interop primitives; ncnn's [Android hardware-buffer notes](https://github.com/Tencent/ncnn/wiki/use-ncnn-with-android-hardware-buffer) do not remove the need to redesign this filter's frame contract. Validate that redesign by device/codec/resolution/refresh-rate test matrix and end-to-end dropped-frame/audio-clock measurements, not by native inference timing alone.
